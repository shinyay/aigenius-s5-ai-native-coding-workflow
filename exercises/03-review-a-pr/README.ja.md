# Exercise 03 -- Draft PRをレビューする

[English](README.md) | 日本語

## この演習のゴール

Copilotが作成したPRを、シニアエンジニアの視点でレビューします。動きそうなコードを眺めるのではなく、Issueとの整合性、失敗時の動作、保守性、安全性、テストの妥当性を根拠を持って判断します。

Copilotは、もっともらしい実装を速く生成できます。しかし、もっともらしさは、正しさや安全性を保証しません。**生成速度はAIが担い、採用できる品質かどうかは人間が判断します。**

---

## 演習

### Step 1 -- Draft PRを開く

1. リポジトリの **Pull Requests** タブを開きます。
2. Exercise 01のIssueからCopilotが作成したDraft PRを選びます。
3. PRが正しいIssueへリンクされ、変更目的が一致しているか確認します。

### Step 2 -- 完全な実行記録を先に読む

PRの説明にあるのは作業の要約であり、完全なセッションログではありません。**Files changed**を見る前に、次を行います。

1. PRまたはIssueの **View session**、またはリポジトリの **Agents** タブから完全な実行記録を開きます。
2. CopilotがIssueをどう理解し、どのファイルや既存テストを調査し、どのコマンドを実行したか確認します。
3. 選んだ設計とその理由、対応しなかった要件、未解決事項を確認します。
4. PRの説明にある要約と完全な実行記録を照合し、抜けや不一致をレビュー対象としてメモします。

先に判断過程を読むと、差分を「何が変わったか」だけでなく、「なぜこの変更になったか」という観点で確認できます。要約、完全な実行記録、実際の差分が一致しない場合も、重要なレビュー項目です。

### Step 3 -- Files changedを確認する

次のチェックリストを上から順に使います。各項目で、**なぜ重要か**と**何を確認するか**を意識してください。

---

## シニアレビューのチェックリスト

### 1. 正確性（Correctness）-- Issueで約束した動作になっているか

**なぜ重要か:** コードが正常に動いても、違う問題を解いていればPRは完成ではありません。

- [ ] 受入条件を1項目ずつ差分またはテストへ対応付けられる
- [ ] CLIの入力、出力、終了コードが期待する動作と一致する
- [ ] 空文字、無効なID、不正な日付、データなしなどの境界条件を扱っている
- [ ] 複数の関数をまたぐ処理を、入力から保存・表示まで追跡した
- [ ] Issueに書かれていない仕様を、Copilotが勝手に追加していない

**判断方法:** 受入条件をPR画面の横へ置き、根拠となるコードまたはテストが見つからない項目へ印を付けます。

### 2. コード品質（Code Quality）-- 次の変更でも安全に扱えるか

**なぜ重要か:** 今回だけ動く実装でも、責務が混在していると次の修正で回帰しやすくなります。

- [ ] 既存の命名、構成、エラー処理のパターンと整合している
- [ ] 関数が1つの責務に集中し、I/Oと変換ロジックが不必要に混在していない
- [ ] 新しい公開関数やクラスに型ヒントとdocstringがある
- [ ] 重複したロジックや、意図の分からない条件分岐が増えていない
- [ ] 変更量がIssueの変更範囲に対して妥当である

**判断方法:** 関数名だけを読んで処理の流れを説明できるか、個別のロジックを単体テストできる構造かを確認します。

### 3. セキュリティ（Security）-- 信頼できない入力や秘密情報を安全に扱うか

**なぜ重要か:** AIが生成したコードも、入力値や外部サービスを自動的に信頼してよいわけではありません。

- [ ] 認証情報、APIキー、接続文字列、実データがハードコードされていない
- [ ] ユーザー入力を利用前に検証している
- [ ] ファイルパス、クエリ、外部コマンドを安全に組み立てている
- [ ] エラーメッセージやログへ秘密情報を出力しない
- [ ] 外部サービスの応答を検証してから利用している

**判断方法:** 「この値を悪意のある内容や想定外の形式に変えたらどうなるか」を入力ごとに考えます。

### 4. 依存関係（Dependencies）-- 追加コストに見合うか

**なぜ重要か:** 依存関係は保守、脆弱性、インストール時間、互換性の責任も追加します。

- [ ] 新しい依存関係が本当に必要で、標準ライブラリや既存の依存関係で代替するより妥当である
- [ ] `requirements.txt`へ正しく宣言されている
- [ ] `import`したライブラリを実際に使用している
- [ ] Issueで指定されたライブラリやバージョン方針に従っている

**判断方法:** 新しい`import`を検索し、利用箇所、依存関係の宣言、テストでの扱いを一組として確認します。

### 5. テスト（Tests）-- 失敗すべきときに失敗できるか

**なぜ重要か:** テストの価値は、実装が壊れたときに検出できることです。成功例だけでは境界条件や回帰を守れません。

- [ ] 既存テストがすべて成功している
- [ ] 新しい動作に対応するテストが追加されている
- [ ] 正常系だけでなく、無効な入力や外部サービスの失敗も確認している
- [ ] テストが実装詳細ではなく、利用者から見える動作を検証している
- [ ] モックが正しい境界にあり、テストから実サービスへ接続しない

**判断方法:** 条件式やエラー経路を一時的に壊したと仮定し、どのテストが検出するか説明できるか考えます。

---

## Step 4 -- 具体的なレビューコメントを残す

チェックリストを確認したら、変更依頼または確認質問を**少なくとも1件**残します。変更行に結び付く指摘はインラインコメントにします。動作自体が存在しない場合や複数ファイルにまたがる指摘は、PR全体へのコメントでも構いません。

曖昧なコメント:

> ここはもう少しよくしてください。

具体的なコメント:

> `task_name`が空文字の場合は検証されていますが、空白だけの`"   "`は保存できてしまいます。保存前に前後の空白を除去し、空になった場合は利用者が修正方法を判断できるエラーメッセージと0以外の終了コードを返すテストを追加してもらえますか？

ほかにも、次のように「観察した事実」「期待する動作」「確認方法」を含めると、修正の往復を減らせます。

> `search`の結果は優先度順ですが、同じ優先度の順序が毎回変わる可能性があります。Issueの受入条件に合わせて`id`の昇順にし、その順序を検証するテストを追加してください。

> 接続エラーをすべて捕捉して空のタスク一覧を返すと、障害と「タスクが0件」を区別できません。利用者向けのエラーを表示して終了コード`1`で終了する設計にした理由、または代替案を説明してもらえますか？

好みだけの指摘ではなく、Issue、既存規約、保守性、リスクのいずれかに結び付けてください。

---

## 振り返り

- 受入条件のうち、コードやテストで根拠を確認できなかったものはありましたか？
- PRの説明にある要約、完全な実行記録、差分の実装は一致していましたか？
- 最もリスクが高い変更はどこで、なぜそう判断しましたか？
- Issueを詳しく書いたことが、レビュー時間や指摘の具体性にどう影響しましたか？
