# Exercise 01 -- 実装につながるIssueを書く

[English](README.md) | 日本語

## この演習のゴール

Copilotが推測に頼らず実装を始められ、あとから人間が結果を客観的に判定できるIssueを書きます。

AIネイティブな開発では、Issueは単なる作業メモではなく、エージェントへ渡す実装仕様です。ただし、長く書くこと自体が目的ではありません。「なぜ必要か」「利用者に何が起きるか」「何を確認できれば完了か」を分けて書くことが重要です。

**この演習で観察すること:** Issueの具体性が、Copilotの調査範囲、実装上の判断、テスト内容にどう反映されるかを、後続のPRで確認します。

---

## 5つの要素を区別する

似て見える項目でも、答える問いが異なります。混ぜずに書くと、実装中とレビュー時の判断基準が明確になります。

| 項目 | 答える問い | 書く内容 |
|---|---|---|
| **Problem statement（解決したい問題）** | なぜ変更が必要ですか？ | 現在の困りごと、影響を受ける利用者、現状の不足 |
| **Desired behavior（期待する動作）** | 完了後、利用者は何ができますか？ | CLIの操作、入力、出力、正常時と失敗時の見え方 |
| **Acceptance criteria（受入条件）** | 各要件をどう判定しますか？ | 実行やテストで確認できる、具体的なチェック項目 |
| **Constraints（制約）** | どの範囲・方法を守る必要がありますか？ | 使用するライブラリ、互換性、秘密情報、変更してはいけないもの |
| **Definition of Done（完了条件）** | PR全体を完了と判断できる状態ですか？ | 受入条件の充足、テスト成功、文書や依存関係の更新、回帰がないこと |

たとえば「検索できるようにする」は期待する動作です。「名前または説明にキーワードを含むタスクが表示される」は受入条件です。「新しい外部検索サービスは追加しない」は制約です。「既存テストと新しい検索テストがすべて成功する」は完了条件です。

## 演習

### Step 1 -- Issueを作成する

1. このリポジトリの **Issues** タブを開きます。
2. **New issue** を選び、**機能リクエスト（日本語）** を開きます。
3. 次の選択肢から1つ選びます。
4. テンプレートのすべての項目を埋め、空欄を残さずにIssueを作成します。

> [!TIP]
> Option AとBはAzureを使う実装へ進むため、後続の実装と検証には利用可能なAzure環境が必要です。Azure環境がない場合は、コアの開発ループではOption CまたはDを選び、オプション Exercise 05でOption AまたはBへ改めて取り組めます。

### Option A -- 保存先をAzure Table Storageへ移行する

現在のローカルJSON保存を、`azure-data-tables`を使ったAzure Table Storageへ移行します。認証情報は環境変数から読み込み、コードやテストへ埋め込んではいけません。既存のCLIコマンドは、利用者から見て今までと同じ操作で動く必要があります。

Issueでは、少なくとも次を決めてください。

- `AZURE_STORAGE_CONNECTION_STRING`が未設定、または接続に失敗した場合の動作
- Taskエンティティの`PartitionKey`と`RowKey`
- 既存データや既存CLIとの互換性
- Azureへ実際に接続せずにテストする方法

### Option B -- Azure OpenAIによるタスク分類を追加する

利用者がタグを指定せずにタスクを追加したとき、Azure OpenAIからカテゴリ候補（例: `work`、`personal`、`health`）を取得し、タグとして設定します。利用者は`--no-ai`でAI呼び出しを無効化できます。認証情報は環境変数から読み込みます。

Issueでは、少なくとも次を決めてください。

- AIを呼び出す条件と、`--tag`や`--no-ai`を指定した場合の優先順位
- API設定が不足している場合、タイムアウトした場合、無効な応答が返った場合の動作
- Azure OpenAIへ送信するデータの範囲
- 外部APIを呼び出さないテスト方法

### Option C -- `search`コマンドを追加する

利用者が`python app.py search "keyword"`を実行すると、名前または説明にキーワードを含むタスクを検索できるようにします。結果は`high`を先頭とする優先度順で表示し、一致した文字列を強調します。

Issueでは、少なくとも次を決めてください。

- 大文字・小文字を区別するか
- 空のキーワード、該当なし、説明がないタスクをどう扱うか
- 同じ優先度内の並び順
- ターミナル上でどのように一致箇所を強調し、テストでどう確認するか

次のコピー用記入例を出発点として利用できます。入力する項目だけを展開し、Issueテンプレートの対応する欄へ貼り付けます。この例を唯一の正解として扱わず、それぞれの仕様上の判断を確認してください。

<details>
<summary><strong>タイトル</strong></summary>

```text
searchコマンドでタスクをキーワード検索できるようにする
```

</details>

<details>
<summary><strong>どのような問題を解決しますか？</strong></summary>

```markdown
現在のタスク管理CLIには、登録済みタスクをキーワードで絞り込む手段がありません。タスク数が増えると、利用者は `list` の全出力を目視して目的のタスクを探す必要があり、名前や説明の一部しか覚えていない場合に時間がかかります。名前または説明からタスクを検索できるコマンドを追加し、必要なタスクへすばやく到達できるようにします。
```

</details>

<details>
<summary><strong>どのような動作を期待しますか？</strong></summary>

```markdown
- 利用者が `python app.py search "keyword"` を実行すると、未完了・完了を含む全タスクから、名前または説明にキーワードを含むタスクを表示する
- 検索は大文字・小文字を区別しない部分一致とする
- 結果は `high`、`medium`、`low` の優先度順に並べ、同じ優先度では `id` の昇順にする
- 結果には少なくともID、名前、説明、優先度、状態を表示し、名前または説明内の一致部分をRichの太字黄色で強調する
- 説明が空または存在しないタスクは、説明を空文字として安全に検索し、表示では `—` とする
- 該当するタスクがない場合は `No tasks match your search.` と表示し、終了コード0で終了する
- キーワードが空文字または空白だけの場合は、修正方法が分かるエラーメッセージを表示し、0以外の終了コードで終了する
```

</details>

<details>
<summary><strong>受入条件</strong></summary>

```markdown
- [ ] `python app.py search --help` にキーワード引数の説明と使用例が表示される
- [ ] 名前にキーワードを含むタスクを、大文字・小文字を区別せず検索できる
- [ ] 説明にのみキーワードを含むタスクも検索できる
- [ ] 未完了・完了の両方のタスクが検索対象になり、結果に状態が表示される
- [ ] 複数件の結果が優先度 `high`、`medium`、`low`、同一優先度では `id` 昇順で表示される
- [ ] 名前と説明の一致部分が太字黄色で強調され、強調対象以外の文字列は変更されない
- [ ] 説明が空またはキー自体が存在しないタスクでも例外が発生しない
- [ ] 該当なしでは `No tasks match your search.` と表示され、終了コードが0になる
- [ ] 空文字または空白だけのキーワードではタスクを表示せず、明確なエラーと0以外の終了コードを返す
- [ ] 正常系、並び順、該当なし、空白入力、説明欠落、強調表示を自動テストで確認できる
```

</details>

<details>
<summary><strong>制約・補足</strong></summary>

```markdown
- 既存のJSONタスクスキーマと、`add`、`list`、`complete`、`edit`、`delete`、`stats`の動作を変更しない
- 検索のための外部サービスや新しい依存ライブラリは追加せず、既存のClickとRichを利用する
- 検索処理はタスクを変更・保存せず、読み取り専用とする
- 既存の`load_tasks()`、優先度定義、色定義などを再利用し、同じロジックを重複させない
- タスク名、説明、検索キーワードをRichのマークアップ文字列として直接連結せず、`Text`などを使って利用者入力がマークアップとして解釈されないようにする
- 強調表示は端末のANSI文字列だけに依存せず、生成したRich `Text`の本文とstyle spanを単体テストできる構造にする
- テストでは既存の`isolated_tasks_file` fixtureを使用し、利用者の実データへアクセスしない
```

</details>

<details>
<summary><strong>完了条件への追加項目</strong></summary>

Issueテンプレートに最初からあるチェック項目は残し、末尾へ次を追加します。

```markdown
- [ ] `README.md`と`app.py`のUsageに`search`コマンドの使用例が追加されている
- [ ] `python app.py search "deploy"`を実行し、期待する結果・並び順・強調表示を手動確認している
```

</details>

各項目を貼り付けたら、**Preview**タブを開き、すべての受入条件と完了条件がチェックボックスとして表示されることを確認してください。

### Option D -- 繰り返しタスクを追加する

`--repeat daily|weekly|monthly`でタスクを繰り返しに設定します。繰り返しタスクを完了すると、次の期限を持つ未完了のコピーを自動作成します。

Issueでは、少なくとも次を決めてください。

- `--repeat`を指定したのに期限がない場合の動作
- 月末、うるう年、異なる月の日数をどう扱うか
- 新しいコピーへ引き継ぐフィールドと、新しく生成するフィールド
- 元の完了済みタスクを履歴として残すか

## 書き終えたら自己レビューする

Issueを送信する前に、次を確認します。

- [ ] Problem statement（解決したい問題）に、現在の問題と変更する理由が書かれている
- [ ] Desired behavior（期待する動作）を、利用者の操作と観察できる結果で説明している
- [ ] Acceptance criteria（受入条件）が、曖昧な表現ではなくYes/Noで判定できる
- [ ] 正常系だけでなく、無効な入力、設定不足、データなしなどの境界条件がある
- [ ] Constraints（制約）に、利用する技術、互換性、秘密情報の扱いがある
- [ ] Definition of Done（完了条件）に、テストと既存機能の回帰確認がある
- [ ] Copilotが判断に迷いそうな点を、意図的に未指定のまま残していない

完全な実装方法まで指示する必要はありません。利用者にとって重要な結果と、守るべき境界は明確にし、内部設計に選択肢がある部分はCopilotの提案をPRで評価します。

## 振り返り

- 「完了した」と客観的に判断するために、どの条件を追加しましたか？
- 人間のチームメンバーなら暗黙に理解しても、Copilotには明示すべき前提は何でしたか？
- Issueを書きながら、まだ決めていなかった仕様に気づきましたか？
- 後続のPRで、Issueのどの記述が実装やテストに反映されたか確認したいですか？
