AIに任せる。
判断は、手放さない。

速くコードを書く、その先へ。
仕事を渡し、根拠を見て、完成へ導く。
Copilot Appは、人間とAIがその一連の作業を進めるための空間です。

Developer Experience（DX）とは、開発者が仕事を進めるときの体験。
この資料では、機能の数ではなく「仕事の何が変わるか」を読み解きます。

これは機能カタログではなく、
ひとつの仕事を完成へ導く
ワークショップの解説資料です。

渡すのは、コードの穴埋めではなく
「判定できる仕事」。

補完は、書いているコードを助けます。エージェントへの委譲では、解くべき問題と完成条件を渡し、変更のまとまりを受け取ります。人間の仕事がなくなるのではなく、判断する場所が、入力の途中から仕事の前後へ広がります。

使い方の比較出典 [1][5]
コード補完を中心に使う

「この続きを書いて」

行や関数を単位に、候補を受け取りながら自分で実装を進める。すぐに編集したい場面に向いています。

タスクを委譲して使う

「この条件を満たす変更を作って」

目的・範囲・受入条件を渡し、差分や実行記録を受け取る。人間は結果を評価し、必要な修正を依頼します。

これは「IDEにはできない」という比較ではありません。IDEにもエージェント機能があります。同じ開発者が、仕事の段階に応じて適した使い方を選びます。

ひとつの仕事を、6つの段階で追う

  1. 01 / DefineIssueで定義

    人間：問題、期待する動作、受入条件、制約、完了条件を決める。

  2. 02 / Delegate作業を委譲

    人間：対象リポジトリと実行範囲を選び、エージェントへ渡す。

  3. 03 / Execute調査・実装・テスト

    AI：既存コードを調べ、変更案と確認に使える成果物を作る。

  4. 04 / Inspect根拠を読む

    人間：Issue、差分、実行記録、テスト結果を対応付ける。

  5. 05 / Iterate修正を重ねる

    人間：事実・期待・確認方法を伝える。AI：同じPRを更新する。

  6. 06 / Accept変更を採用

    人間：要件とルールを満たした変更を、このワークショップでは手動マージする。

図の緑は人間の判断、紫はAIの作業を表します。色だけでなく、各段階の役割名を追ってください。

画面を切り替えるたび、3つの問いに戻る

今の目的は何か。誰の作業か。何がそろえば次へ進めるか。ボタン名を覚える前に、作業の意味を追うと迷いにくくなります。

Copilot Appで、何が変わるのか。

Appの価値は、チャットやターミナルが同じ画面にあることだけではありません。仕事の文脈を保ちながら、任せ方を選び、成果を見て、次の判断へ進めることにあります。

01公式仕様 [4]

ファイル中心から、
タスク中心へ。

「何を編集しているか」だけでなく、「何のための仕事か」を見失わない。

これまでの困りごと
Issue、ターミナル、差分、PRを行き来して、今の作業がどの依頼につながるか探し直す。
体験の変化
My workでIssueやPRを見つけ、Sessionsで個別の作業を進め、ChangesやPRで成果を判断する。1件を最後まで追うときにも意味があります。

ワークショップの題材「タスク名や説明をキーワード検索したい」という目的を、Issue作成からレビュー、マージまで一貫して追います。

話す一言と、誤解させない補足
この変更は、何の仕事で、今どこまで進み、誰の判断を待っているのか。Appは、そのつながりを追う入口になります。

My workとSessionsは役割が異なります。「すべての履歴と情報がひとつの欄にある」とは説明しません。

02公式仕様 [2]

任せる量を、
仕事に合わせて選ぶ。

全部自動か、全部手動か。その二択にしない。

これまでの困りごと
曖昧な依頼をそのまま実装させて手戻りするか、すべての操作を逐次指示してしまう。
体験の変化
Planで範囲と方針を合意し、Interactiveで判断を挟み、定義が十分な仕事はAutopilotへ任せる。モードを作業の段階に合わせます。

ワークショップの題材教材を変更する前に、対象ファイル・日本語対応・表示の仕方を決めてから実装へ進みます。

話す一言と、誤解させない補足
任せるかどうかを一度決めるのではありません。仕事の不確実性に合わせて、任せ方を選びます。

モードが変えるのは協働の進め方です。アクセス権限や本番環境への接続可否を、自動的に安全にする設定ではありません。

03公式仕様 [5]

待つ時間を、
理解する時間へ。

実装を委ねている間、人間は結果を評価する準備を進められる。

これまでの困りごと
AIの生成を見張り続けるか、成果が出てから初めてコードを理解し始める。
体験の変化
cloud agentの作業を背景で進めながら、既存コードや受入条件を確認する。独立したセッションを並行して扱う構成にも広げられます。

ワークショップの題材Codespacesでlist_tasks()を読み、CLIで既存テストとstatsの処理経路を調べます。

話す一言と、誤解させない補足
AIを待つ間に忙しくするのではなく、成果を受け取ったときに判断できる準備をします。

非同期実行は、自動的な時間短縮を保証しません。並行数は、人間が結果を理解し、レビューできる量に合わせます。

04公式仕様 [2]

試すことと、
採用することを分ける。

まず変更案を作り、内容を見てから取り込む。

これまでの困りごと
別の案を試したいが、進行中の作業や安定したコードを巻き込みたくない。
体験の変化
新しいworktreeを選ぶと、ブランチごとの作業ディレクトリで変更案を進められます。採用は差分の確認後に判断します。

ワークショップの題材変更案をPRとして受け取り、差分とテストを確認してから採用します。worktreeは作業を分ける手段であり、本番環境を自動的に隔離する仕組みではありません。

話す一言と、誤解させない補足
AIに試してもらうことと、その変更を採用することを分ける。試行の負担を下げつつ、採用の判断は残します。

worktreeはセキュリティsandboxではありません。共有ポート、認証情報、外部サービス、統合時の競合は別途管理が必要です。

05公式仕様 [3]

会話だけでなく、
同じ成果物で協働する。

説明を読むだけでなく、見える作業面で確認し、操作する。

これまでの困りごと
「修正しました」という返答だけでは、成果物がどう変わったか分からない。
体験の変化
Canvasは人間とエージェントの共有作業面です。文書、ブラウザー、ボードなど、仕事に合う形で進捗や結果を扱えます。

ワークショップの題材AI Genius Slide Presenterは、このリポジトリ独自のProject Canvas extension。人間のボタン操作とエージェントの操作でスライドを進められます。

話す一言と、誤解させない補足
画面は、人間だけが見るものではなくなります。仕事に合う成果物を、人間とAIが扱う共通の作業面にできます。

Slide Presenterは標準搭載機能ではなく、この教材の拡張です。このHTMLはBrowser Canvasで閲覧する解説ページであり、新しいCanvas extensionやリアルタイムの作業監視画面ではありません。

06ワークショップ教材 [7]

個人の試行錯誤を、
次の人の使いやすさへ。

うまく進めた方法を、チャット履歴だけで終わらせない。

これまでの困りごと
よいプロンプトや操作のコツが個人に閉じ、次の人が同じところで迷う。
体験の変化
指示ファイル、Issueテンプレート、回帰テスト、操作手順へ学びを戻す。バージョン管理された共通の前提を育てます。

ワークショップの題材Issue記入例、個別に実行するプロンプト、返信・thread解決・マージの手順を、再利用できる教材として管理します。

話す一言と、誤解させない補足
今日の試行錯誤を、次の人の初期状態にする。AIとの協働も、リポジトリで育てるチームの資産です。

これはモデルが自動学習したという話ではありません。人間が知識を整理し、レビューして共有した成果です。

モードは、仕事の不確実性に合わせる

モード向いている場面人間が見ること
Plan変更範囲や影響がまだ曖昧方針、対象、リスク、完了条件。実装の前に合意する。
Interactive結果を見て仕様を詰めたい曖昧な判断、次の一手、途中の差分。
Autopilot目的と境界が十分に決まっている自律的に進めた結果と根拠。モードを選んでも採否の確認は残す。

Appと実行役を、混同しない。

ワークショップのデモは複数の製品面を使います。すべてを「Appの機能」と呼ぶのではなく、同じ仕事を、適した作業面で進めると説明すると理解しやすくなります。

「Appだけあれば、ほかは不要」とは伝えない

Browser Canvasでgithub.comを表示できることと、そのWeb機能がAppネイティブであることは別です。認証や表示は作業面ごとに確認します。価値は画面遷移の完全なゼロ化ではなく、仕事の文脈を追いやすくすることです。

「全部緑」を、
完成の根拠にしない。

テストの成功は重要な根拠です。ただし、それだけでIssueの期待動作、境界値、変更してはいけない性質まで確認できたとは限りません。AIへ実装を委譲しても、成果を受入条件と照合し、完成へ導く判断は人間が持ち続けます。

レビューの判断軸Exercise 03 [8]Exercise 04 [9]

レビューは、AIの失敗を探す作業ではない

目的は、Issueで約束した価値と、コード・テスト・実行結果が対応しているかを確かめることです。問題があれば、責任追及ではなく、次の修正を判断できる具体的な根拠へ変えます。

4つの問いでPRを読む

  1. 01
    受入条件を、1項目ずつ確認できるか

    PR説明の要約だけでなく、Issueに書いた期待動作と実際の差分・テストを対応付けます。

  2. 02
    通常の例以外に、どの入力で判断するか

    空入力、無効な値、境界値、Unicode、既存データなど、仕様に関係する端を選びます。

  3. 03
    修正後も、守り続ける性質は何か

    個別の例を直すだけでなく、データを失わない、既存動作を変えないといった不変条件を言語化します。

  4. 04
    指摘と修正を、何で再現・確認するか

    事実、期待する動作、再現手順またはテストを分け、再レビューで同じ基準を使います。

感想ではなく、次の行動が分かるフィードバックへ

判断しにくい伝え方

「正しく動きません。直してください」

どの入力で何が起き、何を期待し、どう確認するかが分からないため、修正と再レビューの基準が揃いません。

根拠を持った伝え方

事実 · 期待 · 確認方法

事実: [確認した入力と結果]
期待: [Issueや仕様で求める動作]
確認: [再現手順または追加するテスト]

修正されたことと、採用できることは別

コメントへの返信、コードの更新、review threadの解決、DraftからReady for reviewへの変更、最終マージは別の状態です。Exercise 04では、それぞれを確認しながら同じPRを完成へ導きます。

話す一言と、レビュー用プロンプト
AIの成果をレビューする目的は、失敗を見つけることではありません。受入条件と根拠をつなぎ、変更を採用できる状態へ導くことです。

レビュー：成功の要約ではなく根拠を見る

Compare this PR with the issue's acceptance criteria. Check edge cases and invariants. For each concern, give the evidence, expected behavior, and a reproduction or test. Distinguish verified results from assumptions. Do not change files. Answer in Japanese.

魅力を伝えるために、
できることを言いすぎない。

新しいDXは、何でも自動的に安全になることではありません。どの範囲を委ね、何を確認して採用するかを説明できることが、使う側の安心につながります。

作業分離 ≠ 完全な隔離

worktreeは作業ディレクトリを分けます。外部サービスへの書き込みやポート、認証情報の共有、統合時の競合は別問題です。

Appの画面 ≠ クラウド実行

セッションの実行先には新しいworktree、ローカルリポジトリ、cloud sandboxなどの選択肢があります。「PCを閉じても進む」は実行場所を確認して説明します。

指示ファイル ≠ アクセス制御

「本番に触れない」と指示するだけでなく、実際の権限、秘密情報、ネットワーク、接続ツールを整えます。一時環境という名称だけで保証しません。

実行記録 ≠ 正しさの証明

PR説明は要約です。セッション記録、差分、実行結果を照合します。記録は観察可能な作業の根拠であり、モデルの内部思考を完全に示すものではありません。

自動化できる ≠ 常に自動化する

AppにはAgent Mergeがあります。この教材では、最終判断を学ぶため人間が手動マージします。「Copilotにはマージ機能がない」とは説明しません。

操作完了 ≠ 採用完了

返信する、threadを解決する、Draftを解除する、mainへマージするのは別の操作です。画面の位置より「何の状態を変えたか」を確認します。

実行先・自律性の設定は[2]、Agent Mergeは[4]、教材の手動レビュー・マージ手順は[9]を参照してください。

「速くなった」と言う前に、何を測ったか。

ひとつのデモだけで、生産性が何倍になるかは分かりません。複数エージェントによる同時作業も、無条件に速くなるわけではありません。レビュー可能な粒度、手戻り、成果の採用率、実行コストを一緒に見ます。

明日、ひとつの仕事から始める。

最初から大量のエージェントを並べる必要はありません。小さく定義できる仕事を1件、根拠を持って完成へ導く。そのループをチームで繰り返せることが出発点です。

実践への提案
Developer

開発者

小さな修正を選び、受入条件を言語化する。生成結果に対してどの入力を試せば判断できるかを考えます。

Tech lead

技術リード

生成量より、レビューできる粒度と手戻りを見る。エージェントの並行数を人間の判断能力に合わせます。

Platform team

基盤・開発環境担当

指示、環境、権限、CI、ルールを整える。個人の工夫を安心して委譲できる共通条件へ変えます。

最初の1件で行うこと

  1. 01
    完了を判定できる、小さな課題を選ぶ

    コードの生成量ではなく、利用者に何ができれば完了かを定義します。

  2. 02
    任せ方と境界を決める

    モード、実行場所、変更対象、触れないデータやサービスを明確にします。

  3. 03
    差分と根拠を対応付け、修正を依頼する

    実行記録を読み、受入条件と境界値を確認します。指摘は事実・期待・確認方法の組にします。

  4. 04
    採用したら、学びもリポジトリへ戻す

    不足していた条件、回帰テスト、迷った手順を更新し、次の仕事の初期状態を良くします。

最初に使えるプロンプト：理解・計画

対象Issueやファイルをコンテキストに追加してから使います。以下は操作を実行するボタンではなく、会話へ貼り付ける文章です。

理解：既存のコード経路を追う

Explain how this feature works in this repository. Cite the relevant files and functions, and distinguish what you read from what you executed. Do not change files. Answer in Japanese.

計画：実装の前に範囲を合わせる

Read this issue and the repository instructions. Propose an implementation plan with scope, acceptance criteria, risks, and targeted tests. Identify unresolved assumptions. Do not implement yet. Answer in Japanese.
